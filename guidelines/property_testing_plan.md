# Property-Based Testing Plan for `rust_shunting_yard`

Last reviewed: 2026-06-17

## Purpose

This document explains property-based testing in the context of `rust_shunting_yard` and gives an iterative implementation plan for adding property tests with [`proptest`](https://docs.rs/proptest/latest/proptest/).

The goal is not to replace the existing example-driven tests. The goal is to add a second testing layer that exercises whole families of expressions, parser cases, lexer boundaries, evaluator semantics, and error paths.

The recommended progression is:

1. Start with constrained happy-path properties.
2. Add structured off-nominal properties.
3. Add precedence, associativity, and parser-shape properties.
4. Add recursive generated expressions with an independent reference evaluator.
5. Add broad adversarial input properties for panic and robustness discovery.
6. Persist discovered counterexamples as regression tests.

## What property testing is

A conventional example test says:

> For this one input, I expect this one output.

A property test says:

> For every input generated by this strategy, this invariant must hold.

For `rust_shunting_yard`, example tests are still valuable. They document specific language behaviors and known edge cases. Property tests add value because the important bugs in a calculator/parser/evaluator often appear in combinations:

- operator precedence
- associativity
- parentheses
- lexer token boundaries
- function arity
- numeric promotion
- divide-by-zero and modulo-by-zero behavior
- integer overflow boundaries
- floating-point special cases
- unknown variables
- invalid expression recovery
- malformed syntax
- interactions between lexer, parser, and evaluator

`proptest` uses `Strategy` values to generate test inputs. A strategy controls both how values are generated and how failing values shrink into simpler counterexamples. Shrinking is one of the major reasons to prefer a property-testing framework over ad hoc random tests: when a complex expression fails, the framework attempts to reduce it to a smaller failing expression that is easier to understand.

The most important practical rule is this:

> Generate structured, meaningful inputs first. Generate arbitrary strings only later.

For this repository, the first useful properties should generate valid calculator expressions, valid values, known invalid expressions, and well-scoped edge cases. Broad arbitrary-string testing should be a later robustness layer, closer to fuzz testing.

## Current repo testing shape

The repository already has a natural three-layer testing surface:

1. **Lexer layer**: `tokens.rs` and `lexer.rs`
   - recognizes punctuation, operators, functions, numeric literals, booleans, variables, and lexical errors
   - adapts Logos output into the spanned token form expected by LALRPOP

2. **Parser / AST layer**: `calc.lalrpop` and `ast.rs`
   - constructs `Expression` trees
   - encodes operator precedence and associativity
   - supports function calls and expression lists
   - preserves lexical and parser recovery errors as AST nodes

3. **Evaluator layer**: `eval.rs` and public `evaluate`
   - resolves literals and variables
   - applies unary, binary, and function operations
   - returns `EvalError` variants for known failure modes

The public API `evaluate(text, variables)` is ideal for end-to-end properties because it exercises lexing, parsing, and evaluation together. Internal helper tests are also useful where a helper has a clear semantic contract or defensive branch.

## Dependency setup

The first implementation step should intentionally reintroduce `proptest` as a development dependency.

```toml
[dev-dependencies]
rstest = "0.26.1"
proptest = "1"
```

Use `"1"` rather than pinning a specific old patch version unless there is a project policy that requires exact dependency pins. This allows compatible `1.x` updates while keeping semver boundaries.

## Where to put property tests

Start near the existing tests, then extract only when necessary.

Recommended initial layout:

```text
src/
  eval.rs          # evaluator properties near evaluator tests
  lexer.rs         # lexer properties near lexer tests
  ast.rs           # parser-shape properties near parser tests
  lib.rs           # public evaluate properties
```

As property support code grows, move reusable strategies into one of these:

```text
tests/common/property.rs
```

or:

```text
src/prop_support.rs    # behind #[cfg(test)]
```

Prefer keeping test-only generators private to the test suite. Do not expose them in the public crate API.

## Basic strategy helpers

Start with small, safe domains. Several integer operations currently use primitive `i64` arithmetic directly, so large domains can produce debug-mode overflow panics before the property is actually testing the behavior of interest.

```rust
#[cfg(test)]
mod prop_support {
    use proptest::prelude::*;

    pub fn small_i64() -> impl Strategy<Value = i64> {
        -1_000_000i64..1_000_000
    }

    pub fn nonzero_small_i64() -> impl Strategy<Value = i64> {
        small_i64().prop_filter("non-zero divisor", |v| *v != 0)
    }

    pub fn finite_f64() -> impl Strategy<Value = f64> {
        -1.0e6f64..1.0e6
    }

    pub fn nonzero_finite_f64() -> impl Strategy<Value = f64> {
        finite_f64().prop_filter("non-zero divisor", |v| *v != 0.0)
    }

    pub fn variable_name() -> impl Strategy<Value = String> {
        "[a-zA-Z_][a-zA-Z0-9_]{0,12}".prop_map(String::from)
    }
}
```

Use `prop_filter` sparingly. It is fine for simple constraints such as “nonzero divisor.” For constraints where one generated value determines the valid range of another, prefer `prop_flat_map`.

## Phase 1: Restore low-risk evaluator properties

Start with direct evaluator helper properties. These are deterministic, cheap, and easy to debug.

### Integer comparison properties

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn prop_integer_comparisons_match_rust_ordering(lhs in any::<i64>(), rhs in any::<i64>()) {
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::LessThan, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs < rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::LessThanEquals, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs <= rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::GreaterThan, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs > rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::GreaterThanEquals, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs >= rhs))
        );
    }

    #[test]
    fn prop_integer_equality_matches_rust(lhs in any::<i64>(), rhs in any::<i64>()) {
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::Equals, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs == rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::NotEquals, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs != rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::ApproximatelyEquals, Value::Integer(lhs), Value::Integer(rhs)),
            Ok(Value::Bool(lhs == rhs))
        );
    }
}
```

### Boolean comparison properties

```rust
proptest! {
    #[test]
    fn prop_bool_comparisons_match_rust_ordering(lhs in any::<bool>(), rhs in any::<bool>()) {
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::LessThan, Value::Bool(lhs), Value::Bool(rhs)),
            Ok(Value::Bool(!lhs & rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::LessThanEquals, Value::Bool(lhs), Value::Bool(rhs)),
            Ok(Value::Bool(lhs <= rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::GreaterThan, Value::Bool(lhs), Value::Bool(rhs)),
            Ok(Value::Bool(lhs & !rhs))
        );
        prop_assert_eq!(
            apply_binary_comparison(&Opcode::GreaterThanEquals, Value::Bool(lhs), Value::Bool(rhs)),
            Ok(Value::Bool(lhs >= rhs))
        );
    }
}
```

### Additional low-risk evaluator properties

Add these after comparisons:

| Area | Property |
|---|---|
| unary plus | `+x == x` for integers and finite floats |
| unary minus | `-x` matches Rust for safe integer ranges and finite floats |
| logical not | `!b` matches Rust boolean negation |
| bitwise not | `~i` matches Rust `!i` for integers |
| boolean bitwise ops | `&`, `|`, `^` match Rust boolean bit operations |
| integer bitwise ops | `&`, `|`, `^` match Rust integer bit operations |

Be careful with `i64::MIN` for unary minus, because `-i64::MIN` overflows in debug mode.

## Phase 2: Public API happy-path properties

After helper properties are stable, test through `evaluate`. These tests exercise lexing, parsing, and evaluation together.

### Integer arithmetic

Use small ranges to avoid overflow while the property is focused on correctness of parsing and evaluation.

```rust
use std::collections::HashMap;
use proptest::prelude::*;

proptest! {
    #[test]
    fn prop_evaluate_integer_addition_matches_rust(
        lhs in -1_000_000i64..1_000_000,
        rhs in -1_000_000i64..1_000_000,
    ) {
        let expr = format!("({lhs}) + ({rhs})");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Ok(Value::Integer(lhs + rhs))
        );
    }

    #[test]
    fn prop_evaluate_integer_subtraction_matches_rust(
        lhs in -1_000_000i64..1_000_000,
        rhs in -1_000_000i64..1_000_000,
    ) {
        let expr = format!("({lhs}) - ({rhs})");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Ok(Value::Integer(lhs - rhs))
        );
    }

    #[test]
    fn prop_evaluate_integer_multiplication_matches_rust(
        lhs in -10_000i64..10_000,
        rhs in -10_000i64..10_000,
    ) {
        let expr = format!("({lhs}) * ({rhs})");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Ok(Value::Integer(lhs * rhs))
        );
    }

    #[test]
    fn prop_evaluate_integer_division_matches_rust_for_nonzero_divisors(
        lhs in -1_000_000i64..1_000_000,
        rhs in (-1_000_000i64..1_000_000).prop_filter("nonzero", |v| *v != 0),
    ) {
        let expr = format!("({lhs}) / ({rhs})");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Ok(Value::Integer(lhs / rhs))
        );
    }
}
```

### Variable lookup

The lexer supports variable-like identifiers. Start with conservative variable names that cannot collide with function keywords.

```rust
fn variable_name() -> impl Strategy<Value = String> {
    "[a-zA-Z_][a-zA-Z0-9_]{0,12}".prop_filter(
        "not a reserved function name",
        |s| !matches!(
            s.as_str(),
            "min" | "max" | "pow" | "mod" | "rem" | "round" |
            "cos" | "sin" | "tan" | "acos" | "asin" | "atan" |
            "abs" | "ln" | "log" | "exp" | "floor" | "ceil" | "ceiling"
        ),
    )
}

proptest! {
    #[test]
    fn prop_known_variable_evaluates_to_bound_value(
        name in variable_name(),
        value in -1_000_000i64..1_000_000,
    ) {
        let mut vars = HashMap::new();
        vars.insert(name.clone(), Value::Integer(value));

        prop_assert_eq!(
            evaluate(&name, &vars),
            Ok(Value::Integer(value))
        );
    }

    #[test]
    fn prop_unknown_variable_returns_unknown_variable(name in variable_name()) {
        prop_assert_eq!(
            evaluate(&name, &HashMap::new()),
            Err(EvalError::UnknownVariable(name))
        );
    }
}
```

### Function happy paths

Start with integer-only `min` and `max`.

## Phase 3: Off-nominal properties

Once happy-path properties are stable, generate structured invalid inputs and assert exact failure modes.

### Divide and modulo by zero

```rust
proptest! {
    #[test]
    fn prop_integer_division_by_zero_returns_math_error(lhs in -1_000_000i64..1_000_000) {
        let expr = format!("{lhs} / 0");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Err(EvalError::MathError("Division by zero".to_string()))
        );
    }

    #[test]
    fn prop_integer_modulo_by_zero_returns_math_error(lhs in -1_000_000i64..1_000_000) {
        let expr = format!("{lhs} % 0");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Err(EvalError::MathError("Modulo by zero".to_string()))
        );
    }
}
```

### Bool passed to numeric operations

Generate expressions that are syntactically valid but semantically invalid:

```rust
proptest! {
    #[test]
    fn prop_bool_plus_integer_is_invalid_type(b in any::<bool>(), i in -1000i64..1000) {
        let expr = format!("{b} + {i}");

        prop_assert!(matches!(
            evaluate(&expr, &HashMap::new()),
            Err(EvalError::InvalidType(_))
        ));
    }

    #[test]
    fn prop_min_rejects_bool_argument(b in any::<bool>(), i in -1000i64..1000) {
        let expr = format!("min({b}, {i})");

        prop_assert!(matches!(
            evaluate(&expr, &HashMap::new()),
            Err(EvalError::InvalidType(_))
        ));
    }
}
```

### Function arity errors

The parser supports empty expression lists in function calls. Use that to test invalid arity for functions that require at least one argument.

```rust
#[test]
fn min_empty_returns_invalid_arity() {
    assert_eq!(
        evaluate("min()", &HashMap::new()),
        Err(EvalError::InvalidArity)
    );
}
```

For property tests, generate function names by category:

```rust
fn n_ary_function_name() -> impl Strategy<Value = &'static str> {
    prop_oneof![Just("min"), Just("max")]
}

proptest! {
    #[test]
    fn prop_n_ary_functions_reject_empty_argument_list(func in n_ary_function_name()) {
        let expr = format!("{func}()");

        prop_assert_eq!(
            evaluate(&expr, &HashMap::new()),
            Err(EvalError::InvalidArity)
        );
    }
}
```

## Phase 4: Precedence and associativity properties

Parser properties should mostly be expressed through equivalence. If the parser precedence is correct, then an implicit expression and its explicitly parenthesized form should evaluate the same way.

### Multiplication binds tighter than addition

```rust
proptest! {
    #[test]
    fn prop_multiply_binds_tighter_than_add(
        a in -1000i64..1000,
        b in -1000i64..1000,
        c in -1000i64..1000,
    ) {
        let implicit = format!("{a} + {b} * {c}");
        let explicit = format!("{a} + ({b} * {c})");

        prop_assert_eq!(
            evaluate(&implicit, &HashMap::new()),
            evaluate(&explicit, &HashMap::new())
        );
    }
}
```

### Addition is left-associative

```rust
proptest! {
    #[test]
    fn prop_addition_is_left_associative(
        a in -1000i64..1000,
        b in -1000i64..1000,
        c in -1000i64..1000,
    ) {
        let implicit = format!("{a} + {b} + {c}");
        let explicit = format!("({a} + {b}) + {c}");

        prop_assert_eq!(
            evaluate(&implicit, &HashMap::new()),
            evaluate(&explicit, &HashMap::new())
        );
    }
}
```

### Power is right-associative

Use very small nonnegative integers to avoid overflow and negative exponent behavior while testing parser associativity.

```rust
proptest! {
    #[test]
    fn prop_power_is_right_associative(
        a in 0i64..5,
        b in 0i64..4,
        c in 0i64..3,
    ) {
        let implicit = format!("{a} ** {b} ** {c}");
        let explicit = format!("{a} ** ({b} ** {c})");

        prop_assert_eq!(
            evaluate(&implicit, &HashMap::new()),
            evaluate(&explicit, &HashMap::new())
        );
    }
}
```

### Suggested precedence property matrix

| Property | Equivalence |
|---|---|
| multiplication before addition | `a + b * c == a + (b * c)` |
| division before addition | `a + b / c == a + (b / c)` |
| modulo before addition | `a + b % c == a + (b % c)` |
| addition left-associative | `a + b + c == (a + b) + c` |
| multiplication left-associative | `a * b * c == (a * b) * c` |
| power right-associative | `a ** b ** c == a ** (b ** c)` |
| logical and before logical or | `a || b && c == a || (b && c)` |
| bitwise and before bitwise xor | `a ^ b & c == a ^ (b & c)` |
| bitwise xor before bitwise or | `a | b ^ c == a | (b ^ c)` |

## Phase 5: Lexer properties

The lexer is a good property-testing target because many bugs occur at token boundaries and regex priority boundaries.

### Decimal integers

```rust
proptest! {
    #[test]
    fn prop_decimal_integer_lexes_as_integer(n in 0i64..i64::MAX) {
        let text = n.to_string();
        let mut lexer = lexer::Lexer::new(&text);

        let first = lexer.next();
        prop_assert_eq!(first, Some(Ok((0, tokens::Token::Integer(n), text.len()))));
        prop_assert_eq!(lexer.next(), None);
    }
}
```

### Unknown symbols

```rust
proptest! {
    #[test]
    fn prop_unknown_symbol_becomes_error_token(s in "[@$#]{1,8}") {
        let tokens: Vec<_> = lexer::Lexer::new(&s).collect();

        prop_assert!(
            tokens.iter().any(|tok| matches!(
                tok,
                Ok((_, tokens::Token::Error(_), _))
            ))
        );
    }
}
```

### Lexer property families

| Family | Property |
|---|---|
| decimal integers | `n.to_string()` lexes to `Token::Integer(n)` |
| hexadecimal integers | `format!("0x{:x}", n)` lexes to the matching integer |
| booleans | `true`, `false`, and supported case variants lex to `Token::Bool` |
| valid variables | conservative variable strategy lexes to `Token::Variable` |
| reserved words | function names lex as function tokens, not variables |
| invalid symbols | unknown symbols become `Token::Error` |
| NaN spellings | rejected as invalid float tokens |
| huge integer text | rejected as invalid integer or lexical error |
| huge float text | rejected when infinite, NaN, or subnormal |

## Phase 6: Recursive generated expression trees

Once flat expression properties are reliable, introduce a generated expression tree. The tree should render into calculator source text and, eventually, evaluate through an independent reference evaluator.

Start very small.

```rust
#[derive(Clone, Debug)]
enum PropExpr {
    Int(i64),
    Bool(bool),
    Add(Box<PropExpr>, Box<PropExpr>),
    Mul(Box<PropExpr>, Box<PropExpr>),
    Eq(Box<PropExpr>, Box<PropExpr>),
}

impl PropExpr {
    fn render(&self) -> String {
        match self {
            PropExpr::Int(i) => i.to_string(),
            PropExpr::Bool(b) => b.to_string(),
            PropExpr::Add(a, b) => format!("({} + {})", a.render(), b.render()),
            PropExpr::Mul(a, b) => format!("({} * {})", a.render(), b.render()),
            PropExpr::Eq(a, b) => format!("({} == {})", a.render(), b.render()),
        }
    }
}
```

Then use `prop_recursive` to bound depth, size, and branching.

A first property can simply assert that generated valid expressions do not produce parser errors:

```rust
proptest! {
    #[test]
    fn prop_generated_integer_expression_does_not_parser_error(expr in prop_int_expr()) {
        let text = expr.render();
        let result = evaluate(&text, &HashMap::new());

        prop_assert_ne!(result, Err(EvalError::ParserError));
    }
}
```

The better end-state is to give `PropExpr` a reference evaluator:

```rust
impl PropExpr {
    fn reference_eval(&self) -> Result<Value, EvalError> {
        // A deliberately simple evaluator used only as the property-test oracle.
        // Keep this independent from src/eval.rs so the test does not repeat
        // the same implementation under test.
        todo!()
    }
}
```

Then assert:

```rust
proptest! {
    #[test]
    fn prop_generated_expression_matches_reference_evaluator(expr in prop_expr()) {
        let text = expr.render();

        prop_assert_eq!(
            evaluate(&text, &HashMap::new()),
            expr.reference_eval()
        );
    }
}
```

### Typed expression generation

The recursive generator should become type-aware. Avoid generating `true + 3` in the happy-path generator. That belongs in the off-nominal generator.

Recommended shape:

```rust
enum PropExpr {
    Int(IntExpr),
    Float(FloatExpr),
    Bool(BoolExpr),
}
```

or:

```rust
impl PropExpr {
    fn kind(&self) -> ValueKind {
        // Integer, Float, or Bool
        todo!()
    }
}
```

Type-aware generation allows stronger properties:

- every generated happy-path expression parses successfully
- every generated happy-path expression evaluates successfully
- the rendered expression matches an independent reference evaluator
- generated ill-typed expressions fail with `InvalidType`

## Phase 7: Error-searching and robustness properties

Only after structured properties are in place should you add broad adversarial input generation.

```rust
use proptest::prelude::*;
use proptest::test_runner::Config as ProptestConfig;

proptest! {
    #![proptest_config(ProptestConfig::with_cases(10_000))]

    #[test]
    fn prop_arbitrary_input_never_panics(s in ".{0,256}") {
        let _ = evaluate(&s, &HashMap::new());
    }
}
```

This is not a semantic correctness test. It is a robustness test. It should find panics, parser hangs, Unicode boundary issues, unexpected overflows, and unhandled internal states.

Consider marking it ignored if it becomes expensive:

```rust
#[ignore = "broad adversarial property test; run manually or in nightly CI"]
```

Run manually with:

```bash
PROPTEST_CASES=10000 cargo test prop_arbitrary -- --ignored
```

## Phase 8: Failure persistence and regression workflow

`proptest` can persist failing cases. With the standard library enabled, failure persistence defaults to source-parallel files under `proptest-regressions`.

Recommended workflow:

1. A property test finds a failing generated case.
2. Let `proptest` shrink it.
3. Read the minimal failing case.
4. Decide whether the property or implementation is wrong.
5. If the implementation is wrong, fix it.
6. Commit the persisted regression seed.
7. Add a named example test if the case is important enough to document explicitly.

The persisted regression seed protects against reintroducing the same bug even if random generation does not rediscover it in a future run.

### Acceptance criteria

- The property tests are fast enough for normal development.
- Any persisted regression files caused by real bugs are committed.

## What not to do first

Do not start by generating arbitrary Unicode strings and asserting that `evaluate` does not panic. That is useful later, but it is not the best first property suite.

Do not over-focus on floating-point math in the first PR. Start with finite, bounded values and explicit approximate comparison helpers.

Do not generate full-range integers for happy-path arithmetic until overflow semantics are a deliberate design decision. Some operations may currently use direct primitive arithmetic, while other operations, such as power, are checked more explicitly. Property tests will force that policy question, which is useful, but it should be handled deliberately.

Do not duplicate the evaluator implementation as the reference evaluator. The reference evaluator should be simpler, smaller, and independent. Otherwise the property test may only prove that two copies of the same bug agree.

## Long-term target state

The mature property suite should have three layers.

### 1. Semantic properties

Generated well-typed expressions render to source strings. `evaluate` agrees with an independent reference evaluator.

Examples:

- integer expression semantics
- boolean expression semantics
- mixed integer/float promotion
- function semantics
- variable binding semantics
- precedence and associativity equivalence

### 2. Error properties

Generated malformed or ill-typed expressions fail with the intended `EvalError` variant.

Examples:

- unknown variables return `UnknownVariable`
- numeric functions reject booleans
- invalid arity returns `InvalidArity`
- division by zero returns a math error
- modulo by zero returns a math error
- invalid syntax returns parser errors through the public API

### 3. Robustness properties

Broad generated strings never panic, hang, or violate internal invariants.

Examples:

- arbitrary short input does not panic
- arbitrary operator-heavy input does not panic
- arbitrary Unicode input does not panic
- deeply nested generated expressions are bounded and handled predictably

## Design questions property testing will expose

Property tests are likely to surface semantic questions that should be resolved explicitly.

### Integer overflow policy

Should integer addition, subtraction, multiplication, and bitshifts:

- use Rust debug/release behavior directly,
- wrap intentionally,
- saturate,
- or return `EvalError::MathError` on overflow?

Property tests should initially avoid overflow. Later, add dedicated overflow properties after the policy is decided.

### Float comparison policy

Approximate equality currently needs clear semantic expectations. Decide whether approximate equality should be:

- absolute epsilon,
- relative epsilon,
- mixed absolute/relative,
- or current behavior preserved for compatibility.

Then write properties that encode that policy.

### Function arity policy

Clarify which functions accept:

- exactly one argument,
- exactly two arguments,
- one or two arguments,
- one or more arguments,
- zero or more arguments.

Then generate arity-specific property tests.

### Parser recovery policy

The AST can represent lexical and parser errors. The public API currently collapses parse failures to `ParserError` and evaluation of error AST nodes to `InvalidExpression`. Decide which behaviors are part of the public contract.

## Practical CI tiers

Use separate tiers so normal tests stay fast.

### Local / PR tier

```bash
cargo test
```

Optionally:

```bash
PROPTEST_CASES=1000 cargo test prop_
```

### Nightly or manual deep tier

```bash
PROPTEST_CASES=10000 cargo test prop_
```

### Robustness tier

```bash
PROPTEST_CASES=50000 cargo test prop_arbitrary -- --ignored
```

## Checklist for adding a new property

Before adding a property, answer these questions:

- What is the invariant?
- What input space should be generated?
- What inputs should be excluded, and why?
- Is exclusion better expressed with a constrained generator instead of `prop_filter`?
- Is the oracle independent of the implementation under test?
- Can the failure shrink to a useful minimal example?
- Should the property run in normal `cargo test` or only in a deep/ignored suite?
- If it fails, will the failure indicate a real bug, an underspecified behavior, or a bad generator?

## Recommended implementation order summary

1. Add `proptest` dependency.
2. Add comparison helper properties.
3. Add public integer arithmetic properties with safe ranges.
4. Add division/modulo-by-zero properties.
5. Add known and unknown variable properties.
6. Add `min`/`max` list properties.
7. Add precedence equivalence properties.
8. Add lexer token-boundary properties.
9. Add recursive generated expression trees.
10. Add independent reference evaluator.
11. Add off-nominal generated expression trees.
12. Add broad arbitrary-input robustness properties.
13. Commit meaningful `proptest-regressions` files.
14. Promote important minimized failures into named regression tests.
